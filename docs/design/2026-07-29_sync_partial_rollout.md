# Synchronous partial rollout for the search agent stack — feasibility + PoC design

Date: 2026-07-29. Author: rung-3 session (with user direction). Status: **PoC patch on branch
`sync-partial-rollout-poc` — untested; do not merge while p3v2/rung-4 waves run.**

## 0. Framing (the three separate questions)

1. **Does the feature exist today?** No. `partial_rollout` appears nowhere; the only async
   artifact is verl's `AsyncLLMServerManager` (server-based *generation*, commented out of
   `fit()`), which is unrelated to trajectory preservation.
2. **Is synchronous partial rollout architecturally possible here?** **Yes, cleanly.**
   Partial rollout = preserve unfinished trajectories across rollout cycles and resume
   rather than restart them. Nothing about that requires an async trainer. Our stack is
   unusually well prepared because the CARL phase-2b work already built the resume
   primitives (exact snapshot/restore + offset-aware turn loop).
3. **Does cross-policy resumption require off-policy correction?** For unbiased PPO/GRPO,
   yes in principle; the PoC deliberately ships **without** correction but records
   per-segment provenance so correction can be added and staleness can be measured
   (see §4, R2).

## 1. Code-path analysis

### Rollout side (`agent_system/`)

| Concern | Where | Finding |
|---|---|---|
| Turn loop | `multi_turn_rollout/rollout_loop.py: TrajectoryCollector._turn_loop` | Already resume-aware: takes an arbitrary starting `obs` (from `reset()` **or** `restore_batch()`) and `turn_offsets` (per-slot global depth) — built for CARL phase-2 resumes. Per-cycle budget needed only a `max_steps_override` param. |
| Env snapshot | `env_package/search/.../env.py: SearchEnv.snapshot_state/restore_state` | Complete for resume: `ground_truth`, `max_turns`, `chat_history`, `done`, `turns`, `data_source`. Because `turns` persists, the **global 32-turn horizon stays enforced by the env** across cycles regardless of the per-cycle budget. |
| Pool snapshot | `env_package/search/envs.py: get_states/set_states` | Per-index snapshot/restore over the fixed env pool (pool size = `train_batch_size × rollout.n`, built once). |
| Driver state | `environments/env_manager.py: SearchEnvironmentManager.snapshot/restore_batch` | Carries `SearchMemory` (per-turn action+information history) + task + env state; `rebuild_text_obs` reproduces the policy-visible prompt **byte-identically** (CARL invariant). |
| Slot mapping | `SearchMultiProcessEnv.reset(kwargs)` | Maps `kwargs` onto `envs[0..F)` in order and dummy-resets the rest → resumed trajectories must be restored into **tail** slots *after* the fresh reset (dummy state overwritten). `env_manager.reset()` also sizes `SearchMemory` to `len(kwargs)` only — hence the new `reset_partial()`. |

### Data structures

Per-turn rows are **self-contained dicts** (`input_ids/attention_mask/position_ids/
responses` + non-tensors `uid`, `traj_uid`, `turn_index`, `rewards`, `active_masks`,
`env_done`, …). Trajectory identity is (`traj_uid`, `turn_index`) — *nothing* in
`gather_rollout_data`, `collate_fn`, or `DataProto` assumes rows were generated in the
same cycle or by the same weights. A prefix generated at step k and a suffix at step k+2
concatenate trivially. `adjust_batch` (`multi_turn_rollout/utils.py`) already handles
arbitrary (variable) batch sizes via copy/delete to the LCM divisor — variable per-cycle
release sizes are absorbed there.

### Training side (`verl/trainer/ppo/`)

- **PPO's single-behavior-policy assumption is implicit and silent**: `fit()` recomputes
  `old_log_probs` with the *current pre-update* actor for every row in the training batch
  (`ray_trainer.py`, "recompute old_log_probs" block). On-policy data → this equals the
  behavior policy. A carried segment generated by π_{k-2} gets `old_log_probs` from π_k →
  the PPO ratio starts at 1 and the true importance weight π_k/π_{k-2} is silently
  dropped. The trainer never checks provenance. (When `rollout.calculate_log_probs=True`,
  vLLM behavior logprobs are kept in `rollout_log_probs` and compared as
  `training/rollout_probs_diff*` — the hook for measuring and later correcting this.)
- **GRPO group baseline assumes co-batched groups**: `core_algos.compute_grpo_outcome_advantage`
  computes mean/std over trajectories sharing `uid` *within the training batch*. If group
  members finished in different cycles and were trained separately, each member would be
  baselined against a length-biased subset (early finishers vs early finishers). → PoC
  releases groups atomically.
- **turnPPO/GAE**: values are recomputed by the current critic at train time; cross-turn
  GAE uses `turn_index` + `traj_uid` ordering — works on carried-complete trajectories
  unchanged.
- **Excluding partials until termination**: trivially supported — rows enter training only
  via `gather_rollout_data`; withholding them is a driver-side buffering decision.

## 2. Two semantics

- **Strict on-policy** (resume under the frozen policy until all terminate, then update):
  algorithmically identical to today's vanilla loop — it must still wait for the slowest
  trajectory before updating, with the same straggler idle. Zero staleness, zero
  wall-clock benefit; only useful for bounding per-generation-call memory. Not worth
  building.
- **Cross-update resume** (update, then resume under new weights): this is where the
  benefit lives — every generation call runs with a *full* pool (stragglers deferred and
  re-batched with fresh prompts), so the long tail no longer serializes each step.
  Cost: trajectories contain segments from multiple policy versions → provenance
  recording (done in PoC) and, for unbiased objectives, behavior-logprob-based correction
  (deferred; §4 R2). **The PoC implements cross-update resume with
  exclude-until-complete + group-atomic release.**

## 3. PoC implementation (this branch)

Config (all read via `.get`, no YAML changes; enable with Hydra `+env.partial_rollout_enable=true`):

| Key | Default | Meaning |
|---|---|---|
| `env.partial_rollout_enable` | `False` | Route `multi_turn_loop` to the partial path (train only; val untouched). |
| `env.partial_rollout_cycle_turns` | `env.max_steps` | Per-cycle turn budget. |
| `env.partial_rollout_max_age` | `4` | Drop groups whose pending members span more than this many cycles (staleness bound; dropped groups logged, their compute wasted). |

Changes (4 files, ~250 lines):

1. `rollout_loop.py :: _turn_loop` — `max_steps_override` param; stamps
   `policy_version` (trainer `global_steps` via `gen_batch.meta_info`) on every row.
2. `rollout_loop.py :: partial_multi_turn_loop` (new) — carry buffer
   `self._pr_groups: uid → {born, members, done{traj_uid→rec}, pending{traj_uid→rec}}`
   held in **driver RAM** (rows ≈ 0.5 MB each; worst case pool-bounded ≈ few GB; not
   checkpointed — see R4). Per cycle: drop over-age groups → pack slots
   (fresh groups `[0..F)`, resumed pending `[F..F+R)`; `R ≤ pool` by construction;
   fresh draw shrinks to `(pool−R)/n` groups, surplus dataloader prompts dropped) →
   `_turn_loop(max_steps_override=cycle_turns)` → snapshot unfinished; merge rows into
   buffer → release groups whose every member terminated → `success_evaluator` +
   `_finalize_rollout` on released trajectories only. Returns `None` on empty release.
3. `env_manager.py :: SearchEnvironmentManager.reset_partial` (new) — fresh reset +
   tail-slot restore + memory sized `F+R`.
4. `ray_trainer.py :: fit` — stamps `policy_version`; skips the update on `None`
   (dataloader batch consumed, `global_steps` unchanged); merges `partial/*` metrics
   into wandb.

Emitted metrics: `partial/released_traj, pending_traj, held_complete_traj, open_groups,
dropped_stale_groups, fresh_groups, resumed_traj, mean_open_group_age`.

## 4. Correctness risks

- **R1 — GRPO group split** (baseline bias): *solved structurally* — atomic release.
- **R2 — stale segments trained as on-policy**: recomputed `old_log_probs` under the
  current policy hide the true importance ratio for carried segments. PoC accepts this
  (bounded by PPO clipping + KL penalty + `max_age`), records `policy_version` per row.
  Upgrade path: enable `rollout.calculate_log_probs=True` and, for rows with
  `policy_version < current`, substitute stored `rollout_log_probs` as `old_log_probs`
  (behavior-IS PPO; AReaL's decoupled-PPO is the heavier-duty version). Note vLLM-vs-FSDP
  logprob mismatch (`rollout_probs_diff` ≈ 0.007 mean at p3v2 step 1) bounds the fidelity
  of that substitution.
- **R3 — held-complete staleness**: group-atomic release means early finishers wait for
  siblings, aging alongside them; `max_age` bounds it, dropped groups waste compute.
- **R4 — crash-resume loses the buffer**: workers auto-resume from checkpoints; the carry
  buffer is RAM-only → in-flight trajectories vanish on restart (logged via
  `partial/pending_traj` discontinuity). Acceptable for PoC; persisting the buffer into
  the checkpoint dir is the fix if it matters.
- **R5 — SP3.1 early-stop counters reset across cycles**: `invalid/repeated/no-change`
  windows and `prev_action/prev_obs` are `_turn_loop` locals, so a resumed trajectory's
  counters restart each cycle → early-stop triggers marginally later than vanilla.
  Documented, not carried (smallest-patch tradeoff).
- **R6 — GiGPO/CARL/filter_groups incompatible**: asserted off (anchor-state grouping and
  dynamic sampling both assume same-cycle groups).
- **R7 — epoch/step accounting**: skipped cycles consume dataloader batches without
  updates, and under-drawing discards tail prompts each cycle → an "epoch" no longer
  visits every prompt exactly once. Monitor `partial/fresh_groups` vs 256.
- **R8 — dummy-slot ordering**: resumed state must be restored *after* the pool reset
  (dummy resets touch every env) — encapsulated in `reset_partial`; regression-tested by T1.

## 5. Tests (specified; NOT yet run — this branch is a PoC and has never executed)

- **T1 resume identity (unit)**: run t turns, `snapshot`; `reset_partial([], snaps)`;
  assert `rebuild_text_obs` == the prompt the unbroken path would build (byte equality).
- **T2 frozen-policy equivalence (E2E)**: lr=0, temp=0 (greedy), fixed prompt set:
  vanilla 32-turn vs partial `cycle_turns=8` must produce token-identical trajectories
  and identical released rows (order-independent compare on `traj_uid`).
- **T3 degenerate parity**: `cycle_turns ≥ max_steps` → partial path must equal vanilla
  batch-for-batch (no trajectory ever carries).
- **T4 group-atomic invariant**: every `uid` in a released batch has exactly `n`
  terminated members; assert in test harness over a multi-cycle run.
- **T5 no-double-training**: released `traj_uid` sets are disjoint across cycles.
- **T6 staleness accounting**: with lr>0, carried rows show `policy_version < current`;
  age never exceeds `max_age`.
- **T7 empty-release cycle**: tiny `cycle_turns` forces a `None` cycle; trainer skips
  cleanly, `global_steps` unchanged, next cycle proceeds.
- **T8 throughput A/B**: profiling run vanilla vs partial at the 8B/32-turn config —
  gen-seconds per released trajectory and per-step occupancy (the whole point).

## 6. Open decisions before promoting beyond PoC

1. Behavior-logprob substitution (R2 upgrade) — recommended before any headline run.
2. Buffer persistence across trainer restarts (R4).
3. Prompt-queue instead of drop for the under-draw surplus (R7).
4. Whether `cycle_turns` should be token/time-based rather than turn-based (long turns
   with 1024-token responses vary 10× in wall-clock).

\noindent\small\textit{Scope.} What was done to turn the raw ASearcher QA data into RL-ready training
data for Qwen3-4B-Instruct-2507 with a single \cmd{<search>} tool over local wiki-18 RAG, how the
16k/8-turn context budget was chosen and verified, and the worker/retriever infrastructure that runs it
(including the reliability fixes hard-won during the pass-rate diagnostic). All scripts live under
\cmd{scripts/asearcher/} on branch \cmd{agentic-rl-ca}; commits are referenced inline. Companion
reports: dataset inspection (\cmd{docs/reports/2026-07-25\_asearcher\_audit}), ScienceWorld audit
(\cmd{2026-07-23}).\normalsize

\textbf{Conversion} (\cmd{convert\_base\_to\_parquet.py}, commit \cmd{6d6aff8}): emits the verl/Search-R1
parquet schema (system + user \cmd{prompt}; \cmd{reward\_model.ground\_truth.target};

\emph{deduped union of} \cmd{answer} + \cmd{aug\_answer} aliases, so any alias counts as correct

otherwise). A 512-row validation split is carved (seed 0). First-pass output (pre-filter):
\cmd{data\_asearcher\_base/} = 30{,}318 train + 512 val --- this is what P1/P2 trained on.

\section{Contamination finding and the two-stage filter}
\textbf{Why P2 was killed.} A P1 trajectory dump (384 trajs) showed \textbf{305/384 rollouts issued zero
searches} and \textbf{87/114 correct answers came from parametric memory}. The stage-1 (closed-book)
filter that ASearcher's recipe presumes had been skipped; P2's rising val EM was measuring recall, not
search. Both P2 arms were killed at $\sim$step 60/30 and the data pipeline rebuilt.

\textbf{Stage 1 --- closed-book filter} (\cmd{closed\_book\_filter.py} + \cmd{closed\_book\_worker.sh},
commit \cmd{cbe4ed0}). Offline vLLM (TP=8) samples $n{=}4$ tool-free answers per question
(temp 1.0, top-p 0.95, 160 max tokens, short-answer system prompt) and scores sub-EM against the alias
set; a question answerable from memory is dropped. Throughput $\approx$14.6k tok/s ($\sim$7 min per
split on one 8$\times$H100 worker).

The base histogram is strongly bimodal (the model either knows a fact 4/4 or not at all), so the
$\geq$2/4 threshold separates cleanly. \cmd{keep\_ge2.jsonl} (primary) and strict \cmd{keep\_ge1.jsonl}
are written per split; after also dropping the invalid slice the base diag set is 22{,}418 questions.

\textbf{Stage 2 --- in-setup pass-rate filter} (commit \cmd{bca746b}; running at time of writing).
Each kept question gets \textbf{8 independent in-setup rollouts} (search tool, wiki-18, 8 turns,
temp 1.0) under the base policy, via the trainer's \cmd{val\_only} mode. Two implementation details
matter:
\begin{itemize}
\item \emph{Replication in data, not sampling}: the val env pool is sized \cmd{env\_num =
data.val\_batch\_size} (group\_n = 1), and \cmd{SearchMultiProcessEnv.reset} rejects batches larger than
the pool, so \cmd{val\_kwargs.n{=}8} would crash. Instead \cmd{make\_diag\_parquet.py} writes each
question 8$\times$ adjacent into the val parquet and keeps \cmd{val\_kwargs.n{=}1, do\_sample, T{=}1.0}.
\item \emph{Scoring} (\cmd{passrate\_from\_dump.py}): per-turn rollout dumps
(\cmd{DUMP\_TRAIN\_SAMPLE=1}) are grouped by \cmd{traj\_uid}; the question is parsed from the turn-0
observation; a trajectory passes if \cmd{env\_won} at the terminal turn. Trajectories whose observations
contain retriever-outage markers (\cmd{"Search error:"} / timeout text) are excluded; a question is
scored only with $\geq$4 clean rollouts. The final keep-set is the \textbf{informative-gradient band}
$0 < \mathrm{pass} < n$ (drops all-fail and all-pass questions, which give zero GRPO gradient).
\end{itemize}
After stage 2, \cmd{band\_keep.jsonl} feeds back through the converter to produce the filtered
train/val parquets for the P2 relaunch (token-GRPO vs.\ turn-PPO, then GiGPO/HCAPO).

\section{Training infrastructure}
\textbf{Hardware and launch.} One attached Merlin/Arnold worker (8$\times$H100-SXM-80GB,
\cmd{mlsys\_inference} queue) per condition, launched with \cmd{setsid mlx worker launch \dots}
(client lifetime = script lifetime; workers do not self-terminate --- kill via \cmd{mlx worker kill}).
Each fresh pod re-stages the 61 GB e5 index + 14 GB wiki-18 corpus HDFS$\to$\cmd{/tmp}
($\sim$15--30 min); the training venv and conda retriever env persist on shared \cmd{/home}.

\textbf{Environments.} Training venv \cmd{envs/agentic-rl-ca}: Python 3.11, vLLM 0.11.0,
torch 2.8.0+cu128, flash-attn 2.8.3.post1, verl vendored in-repo. Retriever conda env
\cmd{envs/searchr1-retr-conda} (micromamba, conda-forge): \cmd{python=3.11, mkl=2024.*,
faiss-gpu=1.10.0, pytorch=*=cpu*, transformers, fastapi, uvicorn}. The \textbf{\cmd{mkl=2024.*} pin is
load-bearing}: faiss 1.10 cuda129\_mkl links \cmd{libmkl\_intel\_lp64.so.2}; mkl 2026 ships \cmd{.so.3}
(ImportError). e5 query encoding runs on CPU torch so faiss-gpu owns the CUDA context (commit
\cmd{feb047c}).

\textbf{Retriever serving.} In-repo \cmd{examples/search/retriever/retrieval\_server.py} with
\cmd{--faiss\_gpu}, co-located on the training worker; batch HTTP contract
\cmd{\{"queries": [...]\}} $\to$ \cmd{\{"result": [[\{document, score\}]]\}} (Search-R1 lineage;
schema fix \cmd{d03e302}).

\textbf{Trainer configuration} (\cmd{run\_condition.sh} + protocol): train batch 256 $\times$
group 5 = 1{,}280 trajs/step; \cmd{PPO\_MINI\_BATCH} 512 (locked; \cmd{MICRO\_BSZ} override only
changes gradient-accumulation chunking); LR 1e-6; KL coef 0.001 (low-var-KL in loss for GRPO);
$\gamma{=}1$; 150 steps; val 256 every 25 steps; wandb project
\cmd{ca-rung3-4b-feasibility}. Observed $\sim$442 s/step (generation-dominated at 16k).
\cmd{HF\_DATASETS\_CACHE=/tmp} on every worker (the corpus Arrow cache once filled the shared 125 GB
\cmd{/home}; commit \cmd{89415c8}).

\subsection{Reliability fixes from the stage-2 campaign (2026-07-28)}
Six worker attempts exposed four distinct infra failure modes; all fixes are in
\cmd{diag\_worker4.sh} + wrappers and apply to future long rollout jobs:
\begin{enumerate}
\item \textbf{Pod preflight} (wrappers): some pods arrive without \cmd{libnvidia-ml.so} (CUDA works,
but Ray's pynvml autodetect sees 0 GPUs and dies 10 min in) or with a dead HDFS FUSE mount. Both are
probed with a 3-min retry, then fail-fast so a relaunch draws a fresh pod.
\item \textbf{Retriever watchdog}: health-probe every 2 min; on 3 consecutive failures the server is
restarted. Restart must use \textbf{SIGKILL + wait-for-dead}: SIGTERM leaves uvicorn ``waiting for
connections to close'' forever on hung requests --- the stuck instance holds its GPU shards, the port,
and its micromamba parent.
\item \textbf{No micromamba in the restart path}: micromamba's lock dir lives on shared \cmd{/home}
(\cmd{\textasciitilde/.cache/mamba/proc}) and deadlocks across pods/stuck processes; the watchdog
launches \cmd{\$RETR\_ENV/bin/python} directly.
\item \textbf{BLAS/OMP thread caps} (\cmd{OMP/OPENBLAS/MKL\_NUM\_THREADS=8}): the root cause of the
recurring silent hangs --- e5 CPU encoding at default OMP (=188 cores) under uvicorn's 40-thread pool
livelocks the server. With the caps, the retriever ran hang-free at 1{,}280-trajectory concurrency
(vs.\ restarts every 10--60 min without).
\end{enumerate}
Rollout concurrency for the diagnostic is \cmd{VAL\_BATCH\_OVERRIDE=1280} (P2-proven; 2{,}048
aggravated retriever load). Dumps are written to worker-local \cmd{/tmp} (tens of GB), never shared
\cmd{/home}; only pass-rate summaries + zstd-compressed dumps go to HDFS.
